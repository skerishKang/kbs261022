# CGI 통합 상품 마스터·채널 어댑터 공통 계약 (2026-10-30)

상태: CENTRAL CTO 공통 개발 기준. 범위: 기존 공급처 수집 → 원본 상품 DB → CGI 자체몰 → 네이버 스마트스토어 → 이카운트 ERP. 고객 계약·판매 정책은 이 기술 계약에서 새로 확정하지 않는다.

## 핵심 원칙

1. **상품 정본은 CGI 통합 마스터**(`data/full_catalog/product_db.xlsx` 및 동일 ID로 연결되는 정규화 데이터)이다. 자체몰은 이 정본 4,575건을 표시하는 채널이며 네이버·ERP가 별도 상품 원본을 만들지 않는다. 공급처의 원문·원산지·가격 표기는 보존한다.
2. **원본값(source)과 채널별 변환값(channel projection)을 분리**한다. 네이버 카테고리 코드, ERP 품목코드, 등록 상품번호, 채널별 상태는 별도 필드/연결 테이블로 기록한다. 한 채널의 필수값을 채우기 위해 공급처 원문을 덮어쓰지 않는다.
3. **AI는 상품의 등록 가치·판매 여부·원산지 사실 여부를 임의 판정하지 않는다.** AI의 임무는 수집·필드 매핑·형식변환·누락 검사·API 오류 분석·재시도·증적 보관이다. 불확실하면 원문과 불확실성 그대로 남긴다.
4. **필수 등록 차단은 채널의 실제 스키마 제약, API 실측 거부, 필수 원천값 부재 또는 확인된 중복 충돌로 제한**한다. 내부 임의 점수·검수 선호·ERP 정보 미연결을 네이버 등록 불가의 일반 조건으로 삼지 않는다.
5. **정보 부족과 전체 상품 제외는 구분**한다. 자체몰에서 `가격 문의`로 표시 가능한 상품도 네이버 API에는 실제 숫자 판매가가 필요할 수 있다. 원본이 없으면 채널 미등록 사유로만 기록하고, 자체몰 DB에서 삭제하지 않는다. 제조국·모델명·인증·가격을 추정/허위 생성하지 않는다.
6. **중복은 원천 행 병합과 네이버 채널 중복 방지를 분리**한다. 다른 공급처 원본 두 행이 같은 제품일 가능성만으로 자동 삭제하거나 영구 등록 제외하지 않는다. canonical ID, source IDs, variant IDs, sellerManagementCode와 원상품번호를 추적하며 원격 중복검색을 유지한다.
7. **수정과 동기화는 추적 가능한 단일 마스터 변경 → 채널별 projection 재계산 → 차이 검증 → 채널 적용**의 순서다. 읽기 전용 점검과 실제 쓰기는 분리하고, 기존 판매가·재고·상품번호의 의도치 않은 변경을 막는다.

## 중앙 CTO 변경관리 기준

- **새 필수 필드 또는 API 거부 발견 즉시:** (1) 네이버/ERP 요구 필드와 출처 (2) 자체몰 마스터 보유 여부 (3) 공통 마스터 확장 필요 여부 (4) 다른 채널 영향 (5) 실행 가능한 자동 변환과 진짜 미확보 원천을 함께 기록한다. 사업 선택이 필요한 경우에만 대표에게 선택지를 보고한다.
- 채널 API 요구 때문에 자체몰 화면이나 공급처 원문을 임의 변경하지 않는다. 공통 마스터의 스키마 확장은 채널별 projection과 기존 데이터 호환성을 검증한 뒤 적용한다.
- LOCAL의 BLOCKED 분류는 원인 진단일 뿐 **대표의 판매/등록 제외 결정이 아니다**. 중앙 CTO는 `source_present`, `master_present`, `channel_required`, `adapter_transformable`, `api_rejected`, `true_source_absent`를 교차 검증하고 상품별로 기록한다.
- 네이버 배치14는 로컬 운영 등록 21건/누적 530건 보고가 있었으나 이 기준 문서 작성 당시 GitHub main 장부 병합 여부는 별도 확인 대상이다. 누적 수량과 운영 실측을 혼합하지 않는다.
- ERP 연동도 이 동일 계약을 재사용한다. 별도의 재수집·재심사 파이프라인을 만들지 않는다.

## 구현 수락 기준

1. 4,575개 source ID의 자체몰/마스터/네이버/ERP projection 교차표와 누락·중복 테스트.
2. 기존 차단 4,045건을 **원본 존재 vs API 실제 필수값** 중심으로 재분류하고, 근거 없는 내부 게이트를 제거한 코드·회귀 테스트.
3. 네이버 API의 필수 필드에 유효 원천값이 있는 상품은 기존 등록 러너로 실행, 실제 등록 수·상품번호·오류 확인.
4. ERP는 동일 정본을 수용하는 변환기와 계약 테스트부터 진행. 실제 권한·인증 확보 전 라이브 쓰기 완료로 보고하지 않음.
5. 각 채널의 완료 정의를 분리: DB 포함 / 자체몰 데이터 포함 / 자체몰 운영화면 표시 / 네이버 운영 등록 / ERP 운영 품목 생성. 보고에서 이들을 동일한 `등록 완료`로 합치지 않는다.
