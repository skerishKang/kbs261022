## 02. 사업 목적

### 02.1 김범신 대표가 설명한 목표 (6가지)

| # | 목표 | 성격 |
|---|---|---|
| 1 | CGI의 **기존 홈페이지를 개선**한다. 홈페이지 개편 업체는 이미 연결되어 있다 | 기존 서비스 활용 |
| 2 | 홈페이지에 소개된 상품을 **네이버 스마트스토어 구매 페이지와 연결**한다 | 기존 서비스 연결 |
| 3 | CGI가 취급하는 **제조사·대리점 상품 정보**를 활용해 판매 상품을 등록한다 | 데이터 활용 |
| 4 | 이미 사용 중인 **이카운트 ERP에서 상품·주문·회계 업무를 관리**한다 | 기존 서비스 활용 |
| 5 | **스마트스토어와 이카운트의 기존 연동 기능을 우선 활용**한다 | 재사용 원칙 |
| 6 | 주문·배송·회계전표 자동화는 **실제 업무를 확인하면서 단계적으로 확대**한다 | 단계적 확대 |

### 02.2 이 사업의 성격 — 새 프로그램 3개를 만드는 사업이 아니다

> **이 사업은 CGI 홈페이지·네이버 스마트스토어·이카운트 ERP라는 세 개의 독립 프로그램을 새로 개발하는 사업이 아닙니다.**
> **세 서비스는 이미 존재하고 이미 쓰이고 있습니다.** PADIEM이 하는 일은 **그 사이를 잇는 경로를 만들고, 어디까지 실제로 되는지 확인하는 것**입니다.

**각 서비스가 이미 제공하는 기능은 우선 재사용합니다.** 새로 만드는 것은 연결과 검증에 필요한 최소한의 것에 한정합니다.

### 02.3 이번 단계의 결과 (3단계 구분)

전체 목표는 3단계로 나뉩니다. **1단계가 우선이며, 2·3단계는 1단계 결과와 대표 확인을 거쳐 진행합니다.**

| 단계 | 이름 | 이 단계에서 하는 일 | 선행 조건 |
|---|---|---|---|
| **1단계** | **최소 실증 (우선 2일)** | 준비된 실제 데이터 1건을 이용해 **기술적으로 가능한 경로**를 구현하고 확인한다 | 대표 자료·접근 권한 준비 |
| **2단계** | **추가 연동 검증** | 스마트스토어 개설·인증, 실제 주문 발생 등 **외부 조건이 충족되면** 실제 ERP 연동을 확인한다 | 1단계 결과 + 외부 조건 충족 |
| **3단계** | **상용 구축** | 검증된 결과를 토대로 상품 수 확대, 반복 운영, 주문·배송·회계 자동화를 개발한다 | 1·2단계 결과 + 대표 결정 |

### 02.4 이번 단계에서 기대하는 결과

1. **흐름의 존재 확인** — 홈페이지 → 스마트스토어 → 이카운트로 이어지는 경로 중, 지금 가능한 구간이 어디까지인지 확인한다.
2. **중복 입력 후보 구간의 특정** — 품목·거래처·주문·회계 중 어디가 자동화 후보인지 **구조적으로** 정리한다. *(실제 중복 발생 여부는 1단계에서 확인 — 03.1)*
3. **상용화 결정 근거** — 1·2단계 결과와 대표의 우선순위(08.2 U-07)를 합쳐 3단계 범위와 견적을 결정한다.

### 03.1 자동화 후보 구간 (구조적 분류 — 실제 중복 여부는 1단계에서 확인)

아래는 PADIEM이 **후보가 될 수 있는 구간**을 구조적으로 분류한 것입니다. **중복 입력이 실제로 발생한다고 단정하지 않습니다.** 각 구간의 실제 발생 여부·건수·소요 시간은 1단계 최소 실증에서 함께 확인합니다.

| 구간 | 같은 값이 들어갈 수 있는 두 곳 | 1단계에서 확인할 것 | 현재 상태 |
|---|---|---|---|
| D-1 상품 정보 | 취급 자료 → 스토어 등록, 별도로 ERP 품목 등록 | 동일 정보가 양쪽에 각각 존재하는지 | <span class="tag tag-check">확인필요</span> |
| D-2 품목·거래처 | 스토어 상품 ↔ ERP 품목/거래처 코드 | 매핑이 필요한지, 몇 건인지 | <span class="tag tag-check">확인필요</span> |
| D-3 주문 | 스토어 주문 → ERP 주문서 | 이카운트에 자체 수집 기능이 있는지, **실 계정 미검증** | <span class="tag tag-ai">AI추정</span> (A-02) + <span class="tag tag-check">확인필요</span> |
| D-4 배송 | 발송·송장·출고 상태 | 현재 어느 화면에서 처리하는지 | <span class="tag tag-check">확인필요</span> |
| D-5 회계 전표 | 주문 → 매출/매입 전표 | 이카운트 전표 생성 기능으로 어디까지 줄어드는지, **실 계정 미검증** | <span class="tag tag-ai">AI추정</span> (A-02) + <span class="tag tag-check">확인필요</span> |

> **D-3·D-5에 붙은 <span class="tag tag-ai">AI추정</span>은 "이카운트에 이런 기능이 있을 수 있다"는 PADIEM의 추정**이며, **CGI의 이카운트 계정에서 이미 연결되어 있다는 뜻이 아닙니다.** 실제 지원 여부는 2단계(추가 연동 검증)에서 실 계정으로 확인합니다.

## 05. 단계별 개발 범위

> 단계는 순차적이나, **외부 계정 준비 상태에 따라 병행 또는 보류**될 수 있습니다. 각 단계에 **최소 실증(1단계) / 추가 연동 검증(2단계) / 상용 구축(3단계)** 중 어디 해당하는지 표시했습니다.

| 단계 | 목표 | 해당 | 포함 범위 | 제외 범위 | 완료 조건 | 상태 |
|---|---|---|---|---|---|---|
| **S-0 준비** | 실증을 시작할 수 있는 상태 만들기 | 공통 | 자료 요청, 계정 상태 점검, 작업 환경·저장소 정리 | 실제 연동 | 필요한 자료·권한 확보 여부 확인 | <span class="tag tag-check">대기</span> |
| **S-1 데이터** | 상품 1건의 기준 데이터 만들기 | 1단계 | 대상 상품 1건 확정, 상품명·가격·옵션·사진·식별자 정리, ERP 품목·거래처 매핑 기준 확정, 출처 추적 표 작성 | 상품 다량 정리, 상세페이지 디자인 | 상품 1건이 "어디서 온 데이터인지" 추적 가능 | <span class="tag tag-check">대기</span> |
| **S-2 스토어 개설·등록** | 스마트스토어에서 판매 가능한 상태 만들기 | 1단계(준비) + 2단계(확인) | 스토어 개설 절차 지원, 사업자 인증·계정 상태 확인, 상품 1건 등록(작성 지원), 필요한 옵션·이미지 정리 | 결제 수수료·정산 설계, 상품 다량 등록 | 스토어 관리 화면에서 상품 1건이 **노출 상태** — 개설·인증이 끝나면 구매 가능 여부까지 확인 | <span class="tag tag-check">대기</span> |
| **S-3 홈페이지 구매 경로** | 홈페이지에서 스토어 구매로 이어지는 것 확인 | 1단계 | 상품 1건의 구매 버튼/링크 연결, 클릭 시 스토어 해당 상품 페이지로 이동 확인 | 홈페이지 전면 개편, 디자인 리뉴얼 | **실제 클릭 1회**로 스토어 상품 페이지까지 이동 확인 | <span class="tag tag-check">대기</span> |
| **S-4 ERP 연동 검증** | 이카운트 기능 지원 범위와 실제 연동을 확인 | 1단계(지원 범위 확인) + 2단계(실제 연동) | ERP 실 계정 로그인 → **기능 지원 범위 확인**, 스토어↔ERP 연동 경로 확인, **실제 주문 1건**(또는 대표가 제공한 실제 주문 데이터 1건) ERP 반영·전표화 확인, 결과 검증 | 전량 주문 연동, 반품·교환 자동화, 배송 연동, 회계 마감 자동화 | **확인된 것과 확인되지 않은 것이 구분된 상태**로 기록 | <span class="tag tag-check">대기</span> |
| **S-5 상용 구축** | 검증된 결과를 토대로 상용 시스템화 | 3단계 | 상품 수 확대, 반복 운영, 주문·배송·회계 자동화, 운영 문서, 교육 | 본 문서 범위 | 3단계 별도 결정 | <span class="tag tag-hold">보류</span> |

### 05.1 "완료"와 "미완료" 처리 원칙

- 어떤 단계든 **증거가 없으면 완료로 기재하지 않습니다.** (근거: 화면 캡처, 연결 설정 화면, 전표 번호 등)
- 완료되지 못한 단계는 **사유 + 다음 액면 + 책임자 + 시점을 함께 남깁니다.** 실패를 숨기지 않고 3단계 범위 결정에 입력합니다.
- **1단계 결과가 어떻게 되든 상용화 가능성을 단정하지 않습니다.** 확인된 구간만 3단계 후보로 올립니다.

## 06. 실증 목표와 완료 기준

### 06.1 전체 목표 (한 문장)

> **실제 상품 1건 또는 실제 주문 업무 1건이 "홈페이지 → 스마트스토어 → 이카운트" 흐름을 통과하고, 각 단계의 결과를 사람이 직접 확인·검증할 수 있는 상태를 만든다.**

### 06.2 전체 목표 항목 (C-01~C-06) — 단계별 귀속

> C-01~C-06은 **전체 목표 항목**으로 유지합니다. 다만 **6개 모두를 2일 최소 실증의 필수 통과 조건으로 강제하지 않습니다.** 각 항목이 어느 단계에서 검증되는지는 아래 표로 구분합니다.

| ID | 목표 항목 | 검증 방법 (사람이 직접 확인) | 최소 실증(2일) 필수? | 추가 연동 검증 | 상용 구축 |
|---|---|---|---|---|---|
| **C-01** | 기준 상품 1건이 정리되어 출처가 추적된다 | 상품 시트 1건에 출처(제조사/취급 자료/사진 원본 경로)·가격·옵션·ERP 매핑 대상 기재 | **필수** | — | 상품 수 확대 |
| **C-02** | 스마트스토어가 **개설 완료 상태**임을 확인 | 스토어 판매자 화면에서 상품 1건이 실제 노출·구매 가능 상태 | **외부 조건 충족 시** | **필수** | 다수 상품 등록 |
| **C-03** | 홈페이지 → 스토어 구매 경로가 실제로 동작한다 | 구매 버튼 1회 실제 클릭으로 스토어 상품 페이지 이동 확인(캡처) | **필수** | — | 다수 상품·전면 개편 |
| **C-04** | **실제 주문 1건**이 이카운트에 들어온다 | ERP 주문 수집 화면에서 1건 확인(수집 시각·주문번호 기록) | — | **필수** | 전량 주문 |
| **C-05** | 그 주문이 ERP 전표/장부로 **정확히** 반영된다 | ERP 전표 화면에서 수량·단가·금액·품목이 주문과 대조, 전표번호 기록 | — | **필수** | 전량 전표 자동화 |
| **C-06** | 결과와 남은 문제가 문서로 남는다 | 실행 결과·캡처·설정값·미해결 항목이 산출물로 제출 | **필수** | — | 운영 문서·교육 |

### 06.3 1단계 — 최소 실증 (우선 2일) 필수 통과 조건

> **2일 최소 실증의 성공은 "C-01 + C-03 + C-06" 세 항목이 충족되면 성립합니다.**
> 나머지 C-02·C-04·C-05는 **외부 계정·인증 조건이 충족될 때** 2단계에서 검증합니다. 1단계에서 미검증 상태로 남는 것은 **실패가 아니라 사실 보고**입니다.

| # | 최소 실증 필수 조건 | 왜 이것만 필수인가 |
|---|---|---|
| **M-1** | **실제 상품 1건의 기준 데이터**가 정리되고 출처가 추적된다 (C-01) | 흐름의 출발점. 준비된 실제 데이터 1건으로 가능 |
| **M-2** | **홈페이지 → 스토어 구매 경로 1건**이 실제로 동작함을 확인한다 (C-03) | 목표 흐름의 핵심 연결. 1건이면 가능 |
| **M-3** | **확인한 것과 확인하지 못한 것이 구분된 상태**로 결과가 문서로 남는다 (C-06) | 다음 단계 결정의 근거 |

**M-1~M-3이 충족되면 1단계는 성공으로 보고**, 미충족 항목은 사유와 함께 2단계 입력으로 넘깁니다.

### 06.4 2단계 — 추가 연동 검증 (외부 조건 충족 시)

| 항목 | 선행 외부 조건 | 실패 시 취급 |
|---|---|---|
| C-02 스토어 개설 확인 | 스마트스토어 사업자 인증·계정 개설 완료 | 1단계 결과를 "외부 조건 미충족"으로 명시하고 재시도 일정만 설정 |
| C-04 실제 주문 1건 유입 | 스토어 개설 완료 + 실제 결제 가능 수단 + 대표 제공 주문 1건 | 주문 대신 준비된 실제 데이터로 대체 가능한지 먼저 판단, 대체 시 **검증 강도가 낮음을 명시** |
| C-05 전표 반영 정확성 | C-04 충족 + ERP 계정 권한 | 대조 결과를 그대로 기록 (할인·부가세 반영 방식 포함) |

### 06.5 3단계 — 상용 구축 (이번 문서 범위 밖)

상품 수 확대, 반복 운영, 주문·배송·회계 자동화 구현. **1·2단계 결과와 대표 결정에 따라 범위를 정하며, 본 문서에서 일정·비용을 확정하지 않습니다.**

### 06.6 판정과 기록 원칙

- 각 항목은 **충족 / 미충족 / 판정 불가(외부 조건 미충족)** 로 기록합니다. 판정 불가는 실패가 아니라 사유가 다른 상태입니다.
- **C-02는 스토어 개설 완료가 전제**이므로, 인증이 끝나지 않으면 판정 불가로 남기고 그 상태 자체를 결과로 보고합니다. 완료로 대체 기재하지 않습니다.
- **C-04/C-05의 주문 1건**은 CGI가 실제로 결제한 자기 주문이 검증 가치가 가장 높습니다. 그 외 방법을 사용하면 **어떤 방법이었는지 결과 문서에 명시**합니다.
- **C-05의 "정확히"**는 수량·단가·금액·부가세/할인 반영 여부를 포함합니다. 실제 대조 결과를 그대로 기록합니다. (08.3 A-02)

### 09.1 왜 비교가 필요한가

실증 결과가 3단계(상용화) 결정의 근거가 되므로, **"AI를 사용했을 때 요구사항 누락·오류가 늘지 않는가"**를 확인해야 합니다. 방법론 자체를 문서화해 두어야 합니다.

### 09.2 평가 축

| 평가 축 | 일반 SW 개발 | AI 활용 개발 | 이 사업에서 유의할 점 |
|---|---|---|---|
| 요구사항 반영 누락 | 사람이 빠짐없이 구현하나, 검증 단계에서 발견되는 편이 큼 | 초안 속도가 빠르나 **요구사항 해석이 틀리면 그대로 틀린 상태로 산출** | 대표의 직접 확인이 필수 (11장) |
| 속도 | 요구사항 확인·검토 시간이 전체를 지배 | 산출물 1차 작성은 빠름 | **속도 이득이 확인 시간에서 상쇄되는지** 함께 봄 |
| 검증 가능성 | 테스트 코드를 사람이 작성 | AI가 만든 코드는 사람이 읽고 실행해야 함 | **실행 증거 없이는 통과로 치지 않음** (06장) |
| 수치·단가·계산 | 사람이 직접 입력 | AI가 그럴듯한 값을 생성할 수 있음 | **가격·금액·수량은 반드시 원본 대조** (C-05) |
| 계정·권한·보안 설정 | 매뉴얼 따라 설정 | AI는 실제 계정에 접근 불가 | 설정은 대표/담당자 수행, PADIEM은 화면 확인 (07장) |
| 유지보수 인수인계 | 소스 코드 위주 | 산출물 출처(제어 ID·검토 이력)를 함께 남겨야 함 | GitHub PR 이력을 근거 자료로 활용 |
| 책임 소재 | 개발사 | 개발사 + **대표의 검토·확인** | 본 문서 08.3 / 11장 |

### 09.3 비교 절차 (실증과 동시에 수행)

1. **동일 기준 정의** — 비교 대상은 1단계 산출물(상품 데이터 1건, 구매 링크 1개, ERP 기능 지원 범위 확인 결과)로 고정합니다.
2. **구분 기록** — 각 산출물이 사람이 직접 작성한 것인지 AI가 초안을 작성한 것인지, 대표가 수정한 부분은 무엇인지 PR 이력에 남깁니다.
3. **동일 검증** — 같은 기준으로 사람·AI 산출물을 동일하게 검증합니다. 검증자는 동일하게 "사람이 직접 화면을 확인"합니다.
4. **소요 effort 기록** — 대기 시간(승인·자료·인증 포함)을 분리해 기록합니다. 실제 작업 시간과 대기 시간을 합친 총 소요 시간을 각각 남깁니다.
5. **오류 유형 분류** — 발견된 오류를 "요구사항 해석 오류 / 데이터 입력 오류 / 연동 설정 오류 / 코드·구현 오류"로 분류해 **AI가 유발한 오류인지** 기록합니다.
6. **판정** — 아래 09.4 기준으로 판정하고 결과를 3단계 견적의 근거로 사용합니다.

### 09.4 판정 기준

| 판정 | 기준 |
|---|---|
| **AI 활용 채택** | 요구사항 누락이 없고, 오류가 사람이 즉시 잡아낼 수 있는 수준이며, 총 소요 시간이 단축되었음 |
| **조건부 채택** | 오류가 있으나 대표·담당자가 즉각 발견·수정 가능한 수준. 어떤 구간에 사람이 필수인지 규칙으로 남김 |
| **일반 SW 개발 유지** | 오류 발견 시점이 고객/회계 처리 단계까지 밀리거나, 검증 자체에 사람이 개입해야만 가능 |
| **판정 보류** | 대표 계정·자료 미비로 동일 기준 검증이 불가 |

### 09.5 이 사업에 적용한 원칙 (항상 지킨다)

- AI가 만든 산출물도 **대표가 확인하기 전까지는 확정으로 취급하지 않습니다.**
- **수치(가격·수량·금액·일자)는 원본과 대조**하기 전까지 사용하지 않습니다.
- **계정·권한·인증·결제 설정은 사람이 수행**하고 PADIEM은 화면에서 확인합니다.
- 산출물에 AI 사용 사실과 사람이 개입한 지점을 **PR 이력에 기록**해 3단계 인계에 사용합니다.

## 12. AI 검토 프롬프트

> **사용법** ① 아래 12.1 블록을 복사 ② ② 이 문서 파일(`docs/CGI_업무확인서_개발계획서_AI검토형.md`) 전체를 붙여넣기 ③ ③ AI의 답변을 13장 형식으로 정리해 PADIEM에 전달

### 12.1 기본 검토 프롬프트 (복사해서 사용)

```text
당신은 CGI(중소 제조 대리점)의 이커머스/ERP 통합 프로젝트 기술 검토자입니다.
아래에 붙여넣은 「업무확인서·개발계획서(AI 공동검토형)」를 검토하십시오.

[상황]
- 대상 고객은 CGI 김범신 대표이며, 기술 전문 지식이 제한적입니다.
- CGI는 이미 홈페이지·네이버 스마트스토어·이카운트 ERP를 사용하거나 사용할 계획입니다.
- 이 사업은 세 개의 독립 프로그램을 새로 만드는 사업이 아니라,
  기존 세 서비스의 기능을 재사용하며 연결하는 사업입니다.
- 최초 목표는 2일간의 최소 실증으로 실제 상품 또는 주문 업무 1건을 확인하는 것이며,
  그 결과에 따라 후속 범위를 결정합니다.

[반드시 지켜야 할 검토 원칙]
1. F(확인된 사실) / U(미확인 사항) / A(AI 제안·추정) 세 종류를 반드시 구분하십시오.
   - F는 대표가 직접 진술한 내용입니다. 반박 근거가 부족하면 지적하지 마십시오.
   - U는 대표의 답변이 필요한 항목입니다. 대신 결정하지 말고 "답변이 필요한 항목"으로만 다루십시오.
   - A는 사실이 아닙니다. A를 사실처럼 사용한 문장이 있는지 먼저 찾으십시오.
2. 실증 완료 여부를 임의로 판정하지 마십시오. 문서에 없는 완료 상태를 만들어내지 마십시오.
3. 실제 계정·실제 데이터로 확인하기 전에는 어떤 연동도 "연결된다"고 쓰지 마십시오.
4. 금액·기간·수치는 전제(T-01~T-10)와 함께 제시되어 있는지 확인하고,
   전제가 빠진 수치를 지적하십시오.
5. 가능한 한 짧고 실무적으로 쓰십시오. 길이보다 판단의 정확도가 우선입니다.

[점검할 항목]
A. 사업 목표: 08.1 F-01~F-11이 대표의 실제 목표와 일치하는가?
   빠진 목표가 있거나, 문서에만 있는 목표가 있습니까?
B. 사실과 추정의 분리: F·U·A 표기가 문서 전체에서 일관되게 유지됩니까?
   실제로 중복 입력 발생, ERP 주문 수집·전표 생성, 일정 동의를 단정한 부분이 있습니까?
C. 기존 기능 우선 활용: 각 서비스의 기존 연동 기능을 먼저 쓴다는 원칙이
   실제로 문서의 계획에 반영됩니까? 새로 만들어야 할 것을 PADIEM이 지시하고 있지는 않습니까?
D. 2일 실증의 범위: 06.3 M-1~M-3이 2일 안에 가능한 범위인가요?
   불필요하게 넓거나, 반대로 검증력이 약하지 않나요?
E. 요구사항의 복잡도: 고객이 명시하지 않은 조건을 필수 사업방침으로 만든 부분이 있습니까?
   (예: 필수로 만든 전제, 확정 일정처럼 쓴 참고 시나리오, 고객이 말하지 않은 우선순위)
F. 과속 추정 여부: 실측 근거 없이 낙관적인 표현·수치가 있는가?
G. 실증과 상용의 분리: 1단계(2일)·2단계(추가 연동 검증)·3단계(상용 구축) 구분이
   06장·05장·10장·11장 전체에서 일관되는가?
H. 용어: 비전문가가 읽을 수 없는 설명이 있는가?
I. 빠진 실무 요구사항: 2026-10-22 통화에서 언급된 내용이 문서에 없는 부분은?
   (이 항목은 추정하지 말고, "본문에 근거가 없어 확인이 필요합니다"로만 표시하십시오.)

[출력 형식]
아래 마크다운 표를 그대로 사용하십시오. 각 행마다 한 항목만 다루고,
근거는 반드시 본문의 항목 ID(F-xx/U-xx/A-xx/T-xx/C-xx/M-xx/S-xx)를 인용하십시오.

| 항목 ID | 판정 | 근거(본문 인용) | 권고 수정 | 중요도 |
|---|---|---|---|---|
| (예: A-03) | 적합 / 보완 / 수정필요 / 불명확 | "..." | (구체적 수정안) | 상/중/하 |

판정 값은 다음 4개 중 하나만 사용: 적합 / 보완 / 수정필요 / 불명확
마지막에 「종합 의견」 3~8줄을 추가하십시오. 종합 의견에는
(1) 1단계 최소 실증을 진행해도 되는지, (2) 진행 전에 반드시 확인해야 할 항목 목록,
(3) 이 사업에서 가장 큰 위험 요소 1가지를 포함하십시오.
```

### 12.2 추가 질문용 단축 프롬프트 (필요 시)

```text
아래 「CGI 업무확인서·개발계획서(AI 공동검토형)」의 [항목] 부분만 집중 검토하십시오.
[항목]: (예: 06.3 최소 실증 필수 조건, 10.2 시나리오, 08.3 AI 추정 항목)

추가 지시:

2. 각 지적에 대해 (1) 왜 문제인지 (2) 어떻게 고치면 되는지 (3) 고치면 어떤 효과가 있는지를
   세 줄로 정리하십시오.
3. 문서 밖의 사실은 추정하지 말고 "확인 필요"로 표시하십시오.
```

### 12.3 AI에게 맡기지 말아야 할 것 (PADIEM 판단)

- **계정·권한·인증·결제 설정**: AI는 실제 계정에 접근할 수 없습니다. 사람이 수행해야 합니다.
- **금액·수량·일자 확인**: 원본 대조 없이 AI 산출값을 사용하지 않습니다.
- **실증 완료 판정**: 완료는 증거가 있을 때만 성립합니다 (06장).
- **일정·비용 확정**: AI 추정으로 일정이나 금액을 확정하지 않습니다. (10장)
- **법무·약관·세금 판정**: 스마트스토어 수수료·정산·세무 관련 사항은 대표 및 회계 담당 확인이 필요합니다.
