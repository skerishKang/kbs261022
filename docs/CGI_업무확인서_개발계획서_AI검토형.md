## 01. 이 문서의 사용법

### 01.1 이 문서는 무엇을 위한 것인가

본 문서는 **2026-10-22 통화에서 확인된 요구사항**을 문서화하고, 1차 실증의 범위·완료 기준·전제를 합의하기 위한 **작업 시작 전 확인서**입니다.

이 문서는 다음 두 가지를 합니다.

1. 현재까지 **확인된 사실**, **아직 확인되지 않은 사항**, **AI가 판단한 추정 사항**을 서로 분리해 적습니다.
2. 대표가 이 파일을 자신의 AI에 넣고 **검토·수정·질문**할 수 있도록, 표와 프롬프트 형식을 갖춥니다.

## 02. 사업 목적

### 02.1 목적

CGI가 **기존 홈페이지 → 네이버 스마트스토어 → 이카운트 ERP**로 이어지는 판매·회계 흐름을 한 번에 돌려보고, 상용화 전에 **실제로 무엇이 되고 무엇이 안 되는지**를 1건의 업무로 검증한다.

### 02.2 이번 단계에서 기대하는 결과 (3가지)

1. **흐름의 존재 확인** — 홈페이지에서 스마트스토어로 이동하고, 스마트스토어에서 이카운트로 주문이 들어오는 경로가 실제 계정·실제 데이터로 성립하는지 확인한다.
2. **중복 입력 구간의 특정** — 품목·거래처·주문·회계 중 어느 구간에서 사람이 같은 값을 두 번 입력하고 있는지, 어디를 자동화할 가치가 있는지 **수치 근거 없이 구조적으로** 정리한다.
3. **상용화 결정 근거** — 1차 실증 결과와 대표의 우선순위(08장 U-07)를 합쳐 2단계 구축 범위와 견적을 확정한다.

### 02.3 이 문서의 지위 (이 문서가 아닌 것)

| 이 문서가 **하는** 것 | 이 문서가 **하지 않는** 것 |
|---|---|
| 요구사항 정리·화면 구조 공유·범위 합의 | 실제 연동 개발·스마트스토어 개설·ERP 설정 변경 |
| 완료 기준의 사전 합의 | 상용 시스템 설계·최종 견적 확정 |
| 미확인 사항의 명시적 목록화 | 계정·인증·사업자 등록 대행 |
| 1차 실증 계획 | 2단계(상용화) 일정·비용 확정 |

> 진행 원칙: **이 문서의 11장 검토 결과가 정리되기 전에는 개발 착수하지 않습니다.** 확인되지 않은 상태를 완료로 기재하지 않습니다.

### 06.3 완료 기준에 대한 유의사항

- **C-02는 스토어 개설 완료 자체가 전제**입니다. 인증이 끝나지 않으면 C-02는 판정 불가로 남기고, 그 상태 자체가 실증 결과로 보고합니다. 완료로 대체 기재하지 않습니다.
- **C-04/C-05의 주문 1건**은 CGI가 실제로 결제한 자기 주문이 가장 검증 가치가 높습니다. 그 외 방법(주문 데이터 재사용 등)은 검증 강도가 낮으므로 **어떤 방법이었는지 결과 문서에 명시**합니다.
- **C-05의 "정확히"**는 수량·단가·금액·부가세/할인 반영 여부를 포함합니다. ERP 기본 설정에 따라 할인·부가세 반영 방식이 달라질 수 있으므로, 실제 대조 결과를 그대로 기록합니다. (08장 A-02)

### 06.4 실증 후 결과 분류 (2단계 입력)

| 분류 | 판정 기준 | 2단계로 넘어가는 처리 |

| **부분 통과** | 흐름 일부만 성립 | 통과 구간/미통과 구간을 분리해 2단계 범위 재협의 |

## 09. 일반 SW 개발과 AI 활용 개발의 비교 방법

### 09.1 왜 비교가 필요한가

이번 실증은 "AI로 만들었는가"가 목표가 아니라 **"AI를 사용했을 때 요구사항 누락·오류가 늘지 않는가"**를 확인해야 합니다. 1차 실증 결과가 상용화 결정의 근거가 되므로, **방법론 자체를 문서화**해 두어야 합니다.

### 09.2 평가 축

| 평가 축 | 일반 SW 개발 | AI 활용 개발 | 이 사업에서 유의할 점 |
|---|---|---|---|
| 요구사항 반영 누락 | 사람이 빠짐없이 구현하나, 검증 단계에서 발견되는 편이 큼 | 초안 속도가 빠르나 **요구사항 해석이 틀리면 그대로 틀린 상태로 산출** | 대표의 직접 확인이 필수 (11장) |
| 속도 | 요구사항 확인·검토 시간이 전체를 지배 | 산출물 1차 작성은 빠름 | **속도 이득이 확인 시간에서 상쇄되는지**를 함께 봄 |
| 검증 가능성 | 테스트 코드를 사람이 작성 | AI가 만든 코드는 사람이 읽고 실행해야 함 | **실행 증거 없이는 통과로 치지 않음** (06장) |
| 수치·단가·계산 | 사람이 직접 입력 | AI가 plausible한 값을 생성할 수 있음 | **가격·금액·수량은 반드시 원본 대조** (C-05) |
| 계정·권한·보안 설정 | 매뉴얼 따라 설정 | AI는 실제 계정에 접근 불가 | 설정은 대표/담당자 수행, PADIEM은 화면 확인 (07장) |
| 유지보수 인수인계 | 소스 코드 위주 | 산출물 출처(제어 ID·검토 이력)를 함께 남겨야 함 | GitHub PR 이력을 근거 자료로 활용 |
| 책임 소재 | 개발사 | 개발사 + **대표의 검토·확인** | 본 문서 08.3 / 11장 |

### 09.3 비교 절차 (실증과 동시에 수행)

1. **동일 기준 정의** — 비교 대상은 1차 실증의 S-1~S-4 산출물(상품 데이터 1건, 스토어 등록 1건, 구매 링크 1개, ERP 주문 반영 1건)로 고정합니다.
2. **구분 기록** — 각 산출물이 사람이 직접 작성한 것인지 AI가 초안을 작성한 것인지, 대표가 수정한 부분은 무엇인지 PR 이력에 남깁니다.
3. **동일 검증** — 같은 완료 기준(C-01~C-06)으로 사람·AI 산출물을 동일하게 검증합니다. 검증자는 동일하게 "사람이 직접 화면을 확인"합니다.
4. **소요 effort 기록** — 대기 시간(승인·자료·인증 포함)을 분리해 기록합니다. 대기 시간을 제외한 실제 작업 시간과 대기 시간을 합친 총 소요 시간을 각각 남깁니다.
5. **오류 유형 분류** — 발견된 오류를 "요구사항 해석 오류 / 데이터 입력 오류 / 연동 설정 오류 / 코드·구현 오류"로 분류해, **AI가 유발한 오류인지** 기록합니다.
6. **판정** — 아래 09.4 기준으로 판정하고 결과를 2단계 견적의 근거로 사용합니다.

### 09.4 판정 기준

| 판정 | 기준 |
|---|---|
| **AI 활용 채택** | 요구사항 누락이 없고, 오류가 사람이 즉시 잡아낼 수 있는 수준이며, 총 소요 시간이 단축되었음 |
| **조건부 채택** | 오류가 있으나 대표·담당자가 즉각 발견·수정 가능한 수준. 어떤 구간에 사람이 필수인지 규칙으로 남김 |
| **일반 SW 개발 유지** | 오류 발견 시점이 고객/회계 처리 단계까지 밀리거나, 검증 자체에 사람이 개입해야만 가능 |
| **판정 보류** | 대표 계정·자료 미비로 동일 기준 검증이 불가 |

### 09.5 이 사업에 적용한 원칙 (항상 지킨다)

- AI가 만든 산출물도 **대표가 확인하기 전까지는 확정으로 취급하지 않습니다.**
- **수치(가격·수량·금액·일자)는 원본과 대조**하기 전까지 사용하지 않습니다.
- **계정·권한·인증·결제 설정은 사람이 수행**하고 PADIEM은 화면에서 확인합니다.
- 산출물에 AI 사용 사실과 사람이 개입한 지점을 **PR 이력에 기록**해 2단계 인계에 사용합니다.

- **단일 숫자가 아닌 범위로** 제시하며, 범위의 구성(보수·기준·최소)을 명시합니다.

### 12.3 AI에게 맡기지 말아야 할 것 (PADIEM 판단)

- **계정·권한·인증·결제 설정**: AI는 실제 계정에 접근할 수 없습니다. 사람이 수행해야 합니다.
- **금액·수량·일자 확인**: 원본 대조 없이 AI 산출값을 사용하지 않습니다.
- **실증 완료 판정**: 완료는 증거가 있을 때만 성립합니다 (06.1).
- **법무·약관·세금 판정**: 스마트스토어 수수료·정산·세무 관련 사항은 대표 및 회계 담당 확인이 필요합니다.
