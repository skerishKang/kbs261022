# CGI 이카운트 ERP 실계정 업무 분석 보고서

> **보안 원칙 (본 문서 전체에 적용)**
> - ERP **계정정보(사번·ID·암호·인증키·세션 토큰)는 본 저장소에 기재하지 않는다.** 실제 값은 작업자 로컬 환경에서만 취급했다.
> - **거래처·품목·주문 등 운영 데이터의 실제 행 값은 본 저장소에 기재하지 않는다.** 이 보고서는 *화면 구조·필드명·버튼·규격*만 다룬다. 실데이터는 0건 export 했다.
> - **실운영 데이터의 생성·수정·삭제는 수행하지 않았다.** 조회(GET)·화면 탐색·`엑셀서식내려받기`(빈 서식 파일 다운로드)만 수행했다.
> - 고객(브랜드/품목/거래처) 데이터는 공개 저장소에 포함하지 않는다. 아래 스펙은 **필드 정의와 시스템 동작**에 관한 것이다.

- 대상: 김범신(CGI) 이카운트 ERP 실계정
- 이슈: [#5 / CGI ERP 연계 준비](https://github.com/skerishKang/kbs261022/issues/5) · 관련 [#1 CGI ERP 통합](https://github.com/skerishKang/kbs261022/issues/1)
- 브랜치: `feature/erp-ecount-account-analysis` (origin/main 기준, model-a / model-b 라인과 독립)
- 조사 일자: 2026-10-22
- 브라우저: Playwright(Chromium, 별도 자동화 컨텍스트) — 운영자 개인 Chrome 프로필 미사용

## 0. 완료 지표 (요약)

| 지표 | 결과 | 근거 |
|---|---|---|
| ERP 로그인 | **PASS** | 실계정으로 로그인 후 ERP 셸(菜单 트리·기본그룹·위젯) 진입 확인 |
| 품목 마스터(ITEM_MASTER) | **ANALYZED** | 품목등록(E040103) 리스트·신규(F2) 폼 7탭·변경항목선택 153개 필드·웹자료올리기 템플릿 17컬럼 + 셀 주석(규격) 확인 |
| 재고(INVENTORY) | **ANALYZED** | 재고현황(E040701)·창고등록(E040102)·창고별재고·재고조정·안전재고 필드 확인 |
| 주문(ORDERS) | **ANALYZED** | 주문서입력(E040203)·주문서조회(E040204)·미판매현황(E040212)·판매현황(E040207) 확인 |
| 매출·매입 전표(SALES_SLIPS) | **ANALYZED** | 매출전표 I(E010301)·매입전표 I(E010303) 필드·웹자료올리기 확인 |
| 엑셀 일괄 등록(EXCEL_IMPORT) | **ANALYZED + TEMPLATE ACQUIRED** | `엑셀자료올리기기능`(E000129) 2방식 확인, 품목·거래처·쇼핑몰품목코드연결 템플릿 3종 다운로드·셀주석 파싱 |
| API / 외부 쇼핑몰 연동 | **ANALYZED** | `API인증키발급`(E000125) OAPI 발급·IP등록·매뉴얼 확인, 쇼핑몰관리(C000654) 34몰 지원 매트릭스 확보 |
| **네이버 스마트스토어 연동(NAVER_INTEGRATION)** | **ANALYZED — 부분 지원** | `스마트스토어2.0` 지원: **주문처리 5/5, 클레임처리 7/7, 상품등록 X**, 추가구성품 수집 X. **재고·주문 자동화는 가능, 상품 마스터 자동 등록은 불가** |
| 브라우저 작업 스킬(BROWSER_SKILL) | **DONE** | `skills/ecount-erp-browser/` — 메뉴 경로·필드·버튼·API 스킬 문서 + 프로브 스크립트 |

**핵심 결론 3가지**

1. **이카운트에는 "네이버 스마트스토어 주문 수집·처리" 기능이 실재한다.** `쇼핑몰관리 > 쇼핑몰등록`에 스마트스토어2.0 을 등록하면 신규주문·주문확인(수신/송신)·배송처리·취소·반품·교환 전까지 이카운트 안에서 처리된다. **단, `상품등록`은 지원하지 않는다(X)** — 즉 ERP → 스마트스토어 상품 마스터 자동 배포는 이카운트로 불가하며, 별도 경로가 필요하다.
2. **두 사이트 → 이카운트 품목 등록은 이미 제공된 `웹자료올리기` 기능으로 처리 가능하다.** 품목 마스터 스펙 17컬럼(규격·선택지 포함)이 템플릿로 제공된다. **신규 개발 불필요.**
3. **브랜드·모델명·원산지 같은 이카운트 기본 필드 부재 항목은 `문자형추가항목(cont2~6)` 또는 `추가문자형식(ADD_TXT_01~10)` 확장 필드로 처리해야 한다.** 단 `cont1`은 이미 `조달등록번호`로 사용 중이라 브랜드/모델용으로는 사용할 수 없다.

## 1. ERP 셸 구조

### 1.1 접속·URL 패턴

| 항목 | 값 |
|---|---|
| 로그인 | `https://login.ecount.com/Login?lan_type=ko-KR` (`com_code`=회사코드, `id`, `passwd`) |
| ERP 셸 | `https://loginca.ecount.com/ec56/view/erp?w_flag=1&ec_req_sid=<세션>` |
| 프로그램 URL | `.../view/erp?menuSeq={MENUTREE_xxx}&groupSeq={MENUTREE_xxx}&prgId={E0xxxxx}&depth={n}` |
| 세션 | `ec_req_sid` 쿼리 파라미터. **URL·스크린샷·보고서에 기록 금지** |
| SPA | URL 해시(`#menuType=...`)로 프로그램 전환, 페이지 내부 앵커 이동 없음 |

> **중요**: 이카운트 ERP는 SPA 라우팅이라 화면 이동이 `location.href` 변경이 아니라 **해시 변경 + 내부 렌더**로 일어난다. Playwright 로는 `page.goto()` 대신 **메뉴 검색 UI 클릭**으로 이동해야 한다(§7 스킬에 절차 기록).

2단계 그룹 하위로 3단계 프로그램(실행 화면)이 존재하며, 총 **823개** 프로그램 시드가 API로 노출된다.

### 1.3 메뉴 트리 API (분석 효율화 핵심)

메뉴는 아래 API JSON으로 전체 구조를 받아낼 수 있다(클릭 823회 불필요).

```
GET https://loginca.ecount.com/ec5/api/app.setup/action/menu_setting/GetNavigationTopMenuAction
    ?sid=root|<MENUTREE_sid>&version=<캐시버전>&tenant_sid=<사번>&user_sid=<ID>&ec_req_sid=<세션>
→ { Status, Data: { selected_menu, menu_info{sid:{label,prg_id,depth,parent_sid,children_order}}, sid_mapping_info } }
```
- `sid=root` → 1~2단계, `sid=<2단계 sid>` → 해당 그룹의 3단계 자식(`selected_menu.children_order`)
- **`version` 파라미터를 임의로 바꾸면 빈 응답이 나온다.** 브라우저가 이미 받은 URL 의 version 값을 그대로 재사용해야 한다.
- 3단계 프로그램은 `sid_mapping_info`(823개)에서 `prg_id` 를 얻는다.

> 메뉴는 **왼쪽 네비게이션 DOM 의 텍스트**로도 전부 읽을 수 있다. 가장 빠른 탐색법은 **좌상단 `메뉴검색` 입력창(`#inputFavMSearch`)** — 한국어 2~4자만 입력하면 `prgId` 가 아니라 `menuSeq` 기준으로 후보가 자동완성된다(§7 스킬).

| **품목계층그룹** | `prod_level_group` | 트리(계층)형 그룹. 목록 그리드의 `계층그룹명` 컬럼. **브랜드 축 + 유형 축 계층 표현에 적합** |

| **품목코드** | `prod_cd` | **사용자 정의 문자열, 최대 20자.** 자동채번 강제 없음 |

| **아이템코드 계열** | `item_code` | 이카운트 내부 item_code(옵션 단위). 웹자료올리기 템플릿에는 미노출(스펙 미공개) |

> **판정**: 이카운트는 **카테고리 계층이 3단계(품목그룹) + 별도 트리(품목계층그룹)** 이다. 삼아사운드/삼아스토어의 10단계 웹 카테고리를 그대로 옮길 수는 없고, **리프 카테고리명은 `class_cd3`(또는 품목명 접미사)** 로 내려가고 상위 계층은 `prod_level_group` 으로 올려야 한다. **매핑 규칙은 §5.4 에 명시.**

**권장 아키텍처 (3계열 분리)**

```
[웹 원천]                     [이카운트 ERP]                    [네이버 스마트스토어]
Tri-A(삼아사운드) ─┐
                   ├─► 상품 마스터 CSV ─► 웹자료올리기(품목등록 17컬럼 + 확장)
Tri-B(삼아스토어) ─┘                          │
                                              ├─► ERP 품목코드 (prod_cd)
                                              ├─► ERP 단가(입고/출고)·원가
                                              └─► 쇼핑몰품목코드연결 (ERP품목코드 ↔ 쇼핑몰품목key)
                                                                                │
                     [상품 등록 경로는 별도] ◄───────────────────────────────────┘
                       카페24 API(삼아스토어) 또는 네이버 스마트스토어 OpenAPI 로
                       ERP → 웹 상품 마스터 배포 (이카운트로는 불가)
```

즉 **이카운트 = 주문·재고·회계의 백오피스** 로 확정하고, **상품 마스터 배포는 카페24/네이버 API 를 직접 쓰는 별도 파이프라인**으로 분리하는 것이 현 구조에 맞는 설계다.

### 11.3 웹 카테고리 → ERP 계층 매핑 규칙 (제안)

1. 웹 `source_category_path` 의 **최하위 1단** → `class_cd3` (품목그룹3)
2. 웹 유형 루트(예: 마이크/스피커/레코딩) → `class_cd2` (품목그룹2)
3. 웹 최상위(예: 마이크) → `class_cd1` (품목그룹1)
4. **브랜드 축**은 `prod_level_group`(품목계층그룹) 트리로 분리 — 1개 상품이 그룹 1개에만 속하므로 브랜드와 유형을 동시에 표현할 수 없다 → **브랜드는 `cont2` + `prod_level_group` 조합**으로 처리
5. `remarks_win`(검색창내용) 에 `브랜드 모델명` 을 공백 구분으로 넣어 검색성 확보

> 이 규칙은 **1차 검증 대상**이다(§13 남은 작업).

### 11.4 웹 옵션 ↔ ERP 규격 구조의 불일치 (중요)

| 웹(카페24) | 이카운트 | 결과 |
|---|---|---|
| 옵션 = 자유 텍스트(`길이선택`, `색상` 등) | `SIZE_DES` 규격(문자 1개) + 규격그룹/규격계산 | **1:1 매핑 불가** |
| 옵션값 = 임의 문자열 + 추가금액 | 규격계산그룹 + 단가A~J | 옵션별 추가금액 → `out_price1~10` 매핑 가능 |
| **추가구성상품**(연결 품목) | 이카운트에 개념 없음 | **매핑 불가** → 웹에서 옵션으로 전개하거나, 별도 `연결품목` 관리 필요 |
| 옵션 품절 | `safe`/`safe_qty` + 창고별 안전재고 | 부분 대응 |

> **결론**: 웹 옵션을 이카운트 1차 품목 마스터에 넣지 말고, **ERP 품목 = 웹 상품의 기본 변형 1개**로 두고 옵션 차이는 `out_price1~10` + `ADD_*` 확장필드 또는 별도 스펙으로 관리해야 한다. `추가구성품`은 이카운트로 옮길 수 없다.
