## 1. 결론

**페이앱은 CGI 법인의 초기비용 0원·월/연 유지비 0원 조건을 공식 페이지에 명시하고 있고, 결제·전액취소·부분취소 API와 피드백(알림) 규약을 문서로 제공합니다. 단, "0원"은 예고 없이 종료될 수 있는 무료 이벤트이고, 문서에 명시된 환불 조항으로 종료 후 부과분은 되돌려 받지 않습니다.**

판단에 영향을 세 가지 사실로 압축합니다.

1. **고정비**: 페이앱 유지비 0원, 초기등록비 0원(이벤트, 정상가 120,000원 / 부가세 별도 표기 = 132,000원). 토스는 신청 화면에서 220,000원 + 110,000원 = 330,00원 선납이 확인됐습니다(#106). 1년차 고정비 우위, 2년차부터는 연간 110,000원 차이가 계속 납니다.
2. **고가 장비 취급의 실제 비용은 수수료가 아니라 보증보험 트리거**: 페이앱은 **건당 50만원 이상 또는 월 매출 500만원 이상** 가맹점에 보증보험 가입을 요청할 수 있고, 요청되면 **보험증권 발행 이후에 정산**됩니다. 연 insurance료는 15,000원~71,500원 범위(서울보증보험 납부, 거래 1건이라도 발생하면 해지·환불 불가)로, 토스 선납금보다 작지만 "0원"은 아닙니다.
3. **기술적으로는 재사용 가능하지만 구조가 다릅니다**: 페이앱에는 **서버 간 결제 상태 조회 API가 문서에 없습니다.** 상태 진실은 피드백(webhook) 수신에만 의존합니다. 기존 CGI 코드는 `confirm` 직후 PG 응답으로 상태를 확정하는 흐름이므로, 전환 시 새 수신 엔드포인트와 중복·서명 검증 로직이 추가됩니다.또한 페이앱은 JSON이 아니라 FORM POST + URL-encoded 응답입니다.

**권장**: 전환을 결정하되, (a) 무료 이벤트 종료 여부를 서면으로 확인하고, (b) 보증보험 필요 여부와 정산한도를 업체에 확인한 뒤, (c) 아래 8장의 최소 변경안(어댑터 분리 + 피드백 수신부)으로 진행하는 것이 맞습니다. **실결제 없는 테스트 환경이 없다는 점**(페이앱 "결제 테스트"는 실제 승인이 발생하고 10분 후 자동 취소)을 #71의 토스 Sandbox 검증과 같은 방법으로 재현할 수 없는 조건으로 감수해야 합니다.

### 3.5 보증보험(고가 장비에서 실질 부담이 되는 지점)

- 요청 대상: **건당 결제금액 50만원 이상 또는 월 매출 500만원 이상** 가맹점. 50만원 이하라도 **같은 상품금액을 나눠 결제**하는 경우 요청할 수 있습니다.
- 유의·리스크 업종은 심사 과정에서 추가 요청될 수 있습니다.
- 보험비는 **서울보증보험에 납부**하는 비용이고 페이앱 수취분이 아니며, **거래가 1건이라도 발생하면 해지·환불되지 않습니다.**
- 보증금액 200만 / 300만 / 500만 / 1,000만원, 요율 1.5%·0.715%·0.536%, **연 보험료 15,000 ~ 71,500원**. 문서 표가 평면화되어 첫 행(200만원 ↔ 15,000원)과 요율의 대응은 원문 재확인이 필요합니다. 나머지 쌍은 계산이 맞습니다(300만×0.715%=21,450원, 300만×0.536%=16,080원, 500만×0.715%=35,750원, 500만×0.536%=26,800원, 1,000만×0.715%=71,500원, 1,000만×0.536%=53,600원).
- **CGI 판정**: 장비 단가가 50만원을 넘거나 월 매출이 500만원을 넘는 순간 가입 대상이 됩니다. 연 53,600~71,500원 수준이라 토스 선납 330,000원보다 작지만, "초기·유지비 0원" 홍보와 별개로 CGI에는 실부담이 발생하는 조항입니다.

### 3.6 취소·환불 비용과 절차

- API로 전액취소(`partcancel=0`)와 부분취소(`partcancel=1` + `cancelprice`) 모두 지원.
- 취소 시 정산금 반환: 문서에 별도 위약금·취소수수료는 명시돼 있지 않습니다(미확인). 정산 전 취소는 미정산분에서 제외, 정산 후 취소는 환불 처리 흐름이 일반 PG 구조이나 **페이앱 문서에는 절차가 없어 업체 확인 필요**로 남깁니다.

### 3.7 법인 가입 서류와 심사

법인사업자 제출: 인감 날인 계약서 2부, 법인인감증명서 1부, 사업자등록증 사본 1부, 법인 통장사본 1부. 접수는 이메일(payapp@udid.co.kr)/우편/전자계약서 중 택1. **가입 후 서류 제출 전이라도 결제를 받을 수 있고, 첫 정산 시점에 서류 제출이 필요합니다.** 업종심사에서 유의·리스크 업종은 수수료 인상, 불가 업종은 결제가 취소될 수 있습니다.

### 7-1 기존 CGI 코드 재사용 실측(파일·행 단위)

현재 결제 경로는 이미 어댑터 형태로 짜여 있습니다. 조사 결과 **새 엔진이 필요하지 않습니다.**

- `backend/lib/pg.mjs` (260줄) — `createPgAdapter({secretKey, mode, baseUrl, fetchFn})` 팩토리가 live/mock 두 구현을 같은 인터페이스(`provider`, `mode`, `sandbox`, `live`, `confirm`, `cancel`, `fetchByPaymentKey`, `fetchByOrderId`)로 반환. **주입 가능한 `baseUrl`/`fetchFn` 때문에 페이앱 구현체를 넣을 자리가 이미 있습니다.**
- `backend/worker.js` — 주문 생성(멱등), `/api/payments/confirm`(서버 금액 검증), 관리자 취소, 부분환불 누적·초과 환불 차단, 주문 이벤트 감사 로그. **PG 사에 의존하지 않는 로직입니다.** e2e 18건이 이 부분을 고정합니다(금액 불일치 거부, 같은 paymentKey 재승인 차단, 결제 후 다른 키 = already_paid, 거부된 카드는 재결제 가능, 전액/부분 환불 누적, 환불 멱등).
- D1 `payments` 테이블은 `provider TEXT NOT NULL DEFAULT 'tosspayments'` 칼럼을 이미 갖고 있어(**multi-PG가 스키마에 예고돼 있습니다**), `provider_mode`와 함께 기록됩니다.
- PG 사 지정 리터럴은 총 **3곳**뿐입니다: `worker.js:679`(`provider || 'tosspayments'`), `worker.js:973`(ERP 전송 페이로드에 `pg_provider: 'tosspayments'` 하드코딩), `worker.js:2121`(시크릿 이름 `env.TOSS_WIDGET_SECRET_KEY`). `site/config.js:22`의 `tossJsUrl`과 `site/assets/js/cgi-order.js`의 위젯 호출 2곳(276~293, 394~411)이 클라이언트 측 토스 결합입니다.

**재사용률(행 단위 측정)**: 결제 도메인 로직은 `worker.js` 확인·환불 경로와 e2e 계약 그대로, 변경 대상은 어댑터 1개 파일 + 시크릿 4종 + webhook 라우트 1개 + 클라이언트 결제창 2지점으로 정리됩니다. `pg.mjs` 260줄 중 페이앱과 무관한 재사용부는 인터페이스·에러 클래스·모드 판정부이고, 토스 전용부는 URL/인증/응답 파싱부입니다.

## 8. 최소 변경안(제시) — 이번 조사에서 코드를 변경하지 않은 이유

권장 형태는 **어댑터를 늘리는 것**이지 결제 엔진을 새로 만드는 것이 아닙니다.

1. `backend/lib/pg.mjs`에 `createPayappPgAdapter({userid, linkKey, linkVal, requestKey, baseUrl='https://api.payapp.kr/oapi/v2', fetchFn})` 추가. 기존 인터페이스 중 `confirm`/`cancel`을 구현하고, **`fetchByPaymentKey`/`fetchByOrderId`는 페이앱에 대응 API가 없으므로** `provider`별 capability로 명시적으로 드러냅니다(예: `supportsStatusQuery: false`) — 조용히 토스 응답 형태를 흉내내지 않습니다.
2. FORM POST 인코더 + URL-encoded 응답 파서(키=값 쌍)를 어댑터 안에 추가. 기존 JSON/Bearer 경로와 혼재하지 않게 파일은 그대로 두고 함수 단위로 분리합니다.
3. `feedbackurl` 수신 라우트 1개 신설(예: `POST /api/payments/payapp/feedback`): `hash`·`linkkey`·`linkval`·`userid`·`price`를 문서 규약대로 검증한 뒤, 기존 `order_events`/`payments` 기록부에 반영하고 `SUCCESS`를 평문 응답. `mul_no + pay_state` 기준으로 중복 무시(문서가 가맹점 책임으로 명시).
4. 시크릿 4종을 Worker secret으로 등록(`PAYAPP_USERID`, `PAYAPP_LINK_KEY`, `PAYAPP_LINK_VAL`, `PAYAPP_REQUEST_KEY`). **기존 `TOSS_WIDGET_SECRET_KEY`와 Sandbox 구성은 삭제하지 않고 그대로 유지**합니다.
5. `provider` 리터럴 3곳을 어댑터 값에서 받도록 교체. ERP 전송부(`worker.js:973`)는 `pg_provider`를 인자로 받아야 페이앱 전환 시 전송 데이터가 왜곡되지 않습니다.
6. 클라이언트는 결제창 방식이 다릅니다(인라인 위젯 ↔ 호스팅 `payurl` 리다이렉트). `site/assets/js/cgi-order.js`의 두 지점을 분기하되, 주문 생성·금액·재결제 API는 그대로 씁니다.

**이번에 PR을 내지 않은 판단 근거**: 페이앱에는 실결제 없는 테스트 환경이 없고(7장 10번) 연동 KEY 4종이 없으면 위 경로를 한 줄도 실행할 수 없습니다. 자격증명 없이 작성한 어댑터는 **녹색이 되면서 실제로는 한 번도 호출되지 않은 코드**가 되어, 기존 e2e 18건이 고정하는 안전 속성(금액 불일치 차단·멱등·환불 초과 차단)을 실제로 검증하지 못합니다. 대표 지시 "PG 전환 금지"와 "토스 코드 삭제 금지" 하에, 검증 가능한 증거나 자격증명이 확보된 시점에 같은 규모의 PR로 제출하는 편이 안전합니다.

## 10. 미확인·리스크(가입 전 업체에 물어야 할 목록)

1. **정산한도** — 문서 없음. 고가 장비 주문에서 실질 제약이 될 수 있습니다.
2. **D+3 표기의 현행 적용 여부** — guide5에 "2026년 9월 1일 적용예정" 문구가 남아 있습니다.

5. **정산 후 취소·환불 시 회수 절차** — 페이앱 문서에 절차 없음.
6. **무료 이벤트 종료 시점** — "예고 없이 종료 가능"이 공식 문구입니다. 종료 후 부과되는 등록비는 환불되지 않습니다(약관 명문).
7. **부가세·업종별 추가 요율** — 유의/리스크 업종의 인상 폭은 문서에 수치로 없습니다.
